\section{Arquitectura y MVP técnico}
\label{sec:arquitectura-mvp}

La arquitectura separa dos mundos. El primero es conversacional y flexible: WhatsApp Business, n8n y el agente LLM\@. Allí ocurre la interpretación del lenguaje natural. El segundo es transaccional y determinístico: API REST, PostgreSQL y Admin UI\@. Allí se validan, persisten y operan los pedidos. Esta separación sigue una recomendación común en arquitectura de sistemas con \mbox{IA}: dejar al modelo las tareas de interpretación y explicación, pero reservar el estado de negocio a servicios verificables y auditables~\cite{newman2021,hohpe2003}.

El repositorio actual contiene un backend Spring Boot 3.4 sobre Java 21, con controladores, servicios, repositorios JPA, DTOs, MapStruct, Swagger/OpenAPI y PostgreSQL\@. La API expone recursos para usuarios, productos, órdenes y order-items, incluido el listado de catálogo \texttt{GET /products} incorporado en la integración reciente entre backend y frontend. El ciclo de vida del pedido se modela con siete estados, desde \texttt{IN\_CONFIRMATION} hasta \texttt{COMPLETED}, pasando por pago, preparación y entrega. El frontend administrativo está implementado en React, Vite, TypeScript, Tailwind y shadcn/ui, con modo demo y modo API real. La infraestructura del frontend usa S3 privado y CloudFront, el backend está desplegado externamente en Azure, y ambos despliegues se automatizan con pipelines de integración y entrega continua en GitHub Actions~\cite{humble2010}.

El flujo n8n también está versionado en el repositorio como export JSON de 36 nodos~\cite{n8n2026}. Incluye webhooks de Meta con deduplicación de reintentos, fallback para audio o tipos no soportados, bienvenida con aviso de consentimiento de datos, manejo de imagen de referencia hacia Supabase, agente LangChain sobre un modelo Llama 3.3 70B servido por Groq, memoria conversacional de ventana deslizante, parser de salida estructurada con campos obligatorios, creación de pedido en backend y confirmación o fallback de error. Un detalle coherente con los límites declarados del agente: el workflow no calcula precios; el subtotal se registra en cero y lo confirma el negocio. Esta evidencia técnica permite afirmar que existe un prototipo demostrable. Aun así, la clasificación honesta del estado es la de la Tabla~\ref{tab:estado_tecnico}.

Esta vista de despliegue confirma, con evidencia de infraestructura, la misma disciplina de estados de la Tabla~\ref{tab:estado_tecnico}: el backend y el frontend están implementados y desplegados (Azure y AWS respectivamente), mientras que el hosting gobernado del workflow n8n y la trazabilidad extremo a extremo siguen pendientes para el piloto. El sondeo cada 10 segundos de la Admin UI es una decisión de prototipo, no una garantía de notificación en tiempo real, y debería revisarse antes de operar con clientes reales.
